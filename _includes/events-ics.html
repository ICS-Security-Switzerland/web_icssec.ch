{%- comment -%} An RFC 5545 calendar built from the same _data/events.yml the pages render from, so the calendar cannot drift from what a visitor sees. include.lang 'en' | 'de' | 'fr' | 'it' Every event is included, past ones too: a subscriber's calendar should carry the association's history, and including everything makes the file independent of the build date. Times are written with TZID rather than converted to UTC, and the VTIMEZONE below carries the EU daylight-saving rules so a client can resolve them without guessing. Only DTSTAMP is in UTC, because RFC 5545 requires that. Known deviation: RFC 5545 section 3.1 says content lines longer than 75 octets should be folded, and these are not — the longest DESCRIPTION runs to roughly 300 characters. Liquid can only slice by character, not by octet, so a fold implemented here would not be octet-correct for the accented text this file carries anyway. The output was checked against a conforming parser (python icalendar) and against the four language variants; every client the association is likely to meet accepts unfolded lines. If a strict consumer ever turns up, this is the thing to fix. {%- endcomment -%} {%- assign lang = include.lang -%} {%- assign t = site.data.i18n[lang].events -%} {%- assign prefix = site.data.i18n[lang].prefix -%} {%- assign page_url = prefix | append: 'events/' | absolute_url -%} {%- assign by_date = site.data.events | sort: 'date' -%} {%- comment -%} DTSTAMP must be UTC. site.time is in Europe/Zurich (see _config.yml), and formatting it with a literal "Z" would label local time as UTC — off by one or two hours depending on the season.
